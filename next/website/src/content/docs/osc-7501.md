title: OSC 7501
description: How a program tells Termy Next it's working, needs you, or is done. Termy implements revision 0.3 of the Program Status Protocol.

## The sequence

A program writes an OSC 7501 sequence with colon-separated `key=value` fields, ended by BEL or ST. [Mitchell Hashimoto's write-up](https://mitchellh.com/writing/program-status-osc7501) describes the protocol.

```sh
# Needs permission, with a base64 message ("Hi")
printf '\e]7501;state=blocked:kind=permission:app=deploy:msg=SGk=\a'

# Working, then done
printf '\e]7501;state=working\a'
printf '\e]7501;state=done\a'
```

## Fields

| Field | Meaning |
| --- | --- |
| `state` | `idle`, `working`, `blocked`, `done` or `error`. `clear` removes the record. |
| `kind` | Why it's blocked: `permission`, `question` or `auth`. |
| `progress` | A percentage, from 0 to 100. |
| `app` | The program's name, up to 32 characters. Child records inherit it. |
| `title` | Base64 text the tab shows while working. |
| `msg` | Base64 text the Activity popup shows. |
| `id` | A record ID. `/` nests records, such as `build/test`; omit it for the root record. |

A report that fails validation is ignored as a whole. A pane keeps up to 256 records.

## Detection

Send `\e]7501;?` and Termy answers with the same sequence, so a program can check for support before it reports.

## What Termy Next shows

States appear on tabs and in the Activity popup, described in [Agents and activity](/docs/agents). Plugins can read them with `block.call(…, "program_status")` or listen for `block_event`.
